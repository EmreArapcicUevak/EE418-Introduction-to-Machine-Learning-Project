	\section{Introduction to the Problem}
		A major problem a lot of people face is that they do not know how to price their apartments
		or how to check for the \emph{"fairness"} (If the given price matches real expectation) of
		a given price. \newline

		\noindent This problem also extends to renting as sometimes people are not sure what
		they should or could put as their monthly rent price nor do tenants know if the given rentals
		are worth the given renting price. Of course this is taking into consideration that the tenant has other options. \newline

		\noindent Our goal for this project was to test out a suite of \emph{hypothesis spaces} (machine learning model classes)
		to see if we could get out a \emph{hypothesis} (model) that could accurately predict the prices of apartments that are
		either being sold or rented out.

	\section{Materials and Methods}
		\subsection{Data Acquisition}
			\noindent We decided to first focus on the canton of Sarajevo as it was the best option
			for us to create a proof of concept for Bosnia and Herzegovina. \newline

			\noindent Since there is a lack of information regarding apartments that were sold and their
			features in Bosnia and herzegovina we decided to webscrape the information from popular website like:
			\begin{itemize}
				\item \href{https://olx.ba}{OLX.ba}
				\item \href{https://nekretnine.ba}{nekretnine.ba}
			\end{itemize}

			\noindent however since the data presented on these two was different we found it easiest
			to work with apartments listed on the \href{https://olx.ba}{OLX.ba}. \newline

			\noindent Once we finished scraping the data, we uploaded it to kagglehub
			as it would be much easier to just update the dataset on kagglehub and download it from kagglehub
			whenever we wish to retrain the model rather than just saving it locally. \newline

			\noindent The dataset is available \href{https://www.kaggle.com/datasets/mustafasinanovic/sarajevo-flats}{here}.

		\pagebreak
		\subsection{Data Overview}
			The data we were able to get from every entry from \olx~is as follows:
			\begin{itemize}
				\item[title] The title of the post
				\item[url] The url to the post
				\item[price\_numeric] The numeric price of the apartment (either the renting or selling price)
				\item[municipality] The municipality the apartment is located in
				\item[rooms] The number of rooms the apartment has
				\item[square\_m2] The $m^2$ of an apartment
				\item[condition] The condition of the apartment
				\item[ad\_type] If the apartment is listed for sale or for renting
				\item[property\_type] Apartments labeled as either "Stan" or "Apartman" (More about this later)
				\item[equipment] Feature that tells us how furnished the apartment is
				\item[level] The floor the apartment is located on
				\item[heating] The type of heating the apartment is using
				\item[latitude] The latitude coordinate of the apartment
				\item[longitude] The longitude coordinate of the apartment
			\end{itemize}

			\subsubsection{Missing Values}
				Let's first plot out to see what amounts of missing features do we exactly have in our dataset that is currently missing,
				and then we will try to see if there are any correlations betweens features that are missing.

				\begin{figure}[h]
					\centering

				\end{figure}

				\noindent As we can see from Figure~\ref{fig:Missing Feature Bar Plot}~we do have around $1806$ entries, however there are certain things that we just
				cannot work with. First if we take a look at the price, which is our \emph{target variable}, we will see that we only have 1428. This is to be

				\noindent Another issue with imputation of the prices is the fact that the distributions of features of apartments with and without the prices are not the same

				as we would have to impute looking at the entire dataset. \newline

				\noindent Another thing we have missing is the number of rooms.
				Luckily for us, we do not have a lot of apartments with missing rooms and unlike prices we can actually impute these with relatively low risk.
				However, there is one issue and it has to do with the next variable.

				\noindent Another concern, apart from prices, is actually the coordinates. As can be seen we only have 1175 apartments that have coordinate,
				and we still don't know how many of the apartment with coordinate have prices. To be sure lets plot a matrix plot of the missing values and a
				heatmap to see if there could be any correlation between them.

		\subsection{Feature Engineering}
			\subsubsection{Feature Selection}
			\label{sec:Feature Selection}

			\noindent When it comes to feature selection we do not have a lot of issues. Looking back at Table~\ref{tab:feature_domains} we can immidietly
			see that we do not need things like 'title' and 'url'. \newline

			\noindent As we talked about in section~\ref{subsubsec: Data Cleaning} the feature 'property_type' is not that useful and keeping it will cause
			more trouble than good as it has a high class imbalance, hence we decided to get rid of it as well. \newline

			\noindent The harder question that we asked ourselves was if we wanted to keep the coordinates (longitude and latitude) or not,
			since a lot of apartments would be removed if we were to get rid of coordinates as there was no way to impute the coordinates.
			And to answer this question we looked back about what we said about the 'municipality' feature; when thinking of how someone would
			price their own home we though, okay if the houses are approximately in the same location, look the same, and so on, that their prices
			would be close. \newline

			\noindent However, the main issue with this was the sheer fact that without coordinates we only had to rely on the municipality feature for the
			general location and other available features on hand. The problem? Municipality is not a good indicator of location-based price variation.
			Figure~\ref{fig: Novi Grad} shows a municipality that contains multiple apartments equal when it comes to features, but different when it comes
			to prices.

			\begin{figure}[H]
					\centering
					\includegraphics[width=0.7\textwidth]{../ProjectPitch/Images/NoviGradMap}
					\caption{Municipality of Novi Grad Sarajevo}
					\label{fig: Novi Grad}
			\end{figure}

			\noindent And in practice when we tried to train models on just these features themselves the models performed horribly. On data that models
			never saw before the best values we got were all around $R^2 = 0.12$! And this made us realize that coordinates had to stay. \newline

			\noindent Whether we should keep municipalities or not as features, we decided to stratify the train and test split using the municipality
			feature as this would make sure that we got a nice sample of apartments around the entire canton, however when it came to keeping it for training
			we did some testing and models performed way better without it then with it. \newline

			\noindent Another important thing to mention is that the models themselves also did feature selection as a part of hyperparameter tuning.

		\subsection{Methods}
			\subsubsection{Model Selection}
				\label{subsubsec:Model Selection}

				\noindent When it comes to model selection we used scikit's default parameter models to quickly get an overall image of how well these models
				would perform, of course the selection of these models was based on our knowledge of how they worked and the knowledge about the problem domain. \newline

				\noindent The models were quickly trained on the training data and were then compared to the "base" error, the error the model makes
				if it predicts that all the apartments have the same mean price, and after trying all of them out the best performing models were:
				\begin{itemize}
					\item Random Forest Regressor
					\item Linear Regression
					\item K Nearest Neighbors Regressor
					\item Support Vector Machines
					\item Gradient Boosting Regressor
				\end{itemize}


			\subsubsection{Parameter Optimization}

				\noindent
				For each model class introduced in Section~\ref{subsubsec:Model Selection}, an extensive hyperparameter search was conducted using a predefined parameter grid.
				The goal of this procedure was not only to improve predictive performance, but also to evaluate the sensitivity of each model to its most influential hyperparameters.

				\medskip
				\noindent
				All hyperparameter combinations were evaluated using cross-validation on the training set.
				In addition to the standard model formulations, we also evaluated variants where the target variable was transformed using a logarithmic mapping via a \texttt{TransformedTargetRegressor}.
				This was motivated by the strong right-skewness typically observed in real estate price distributions (Figure~\ref{fig:pre_clean_price_numeric_distribution}).

				\paragraph{Random Forest Regressor}
				\noindent
				For the Random Forest model, we explored a wide range of structural and regularization-related hyperparameters.
				Specifically, the number of trees was varied to balance model stability and computational cost, while tree depth and minimum sample thresholds were adjusted to control overfitting.
				Both standard Random Forest models and logarithmically transformed target variants were evaluated.

				\begin{itemize}
					\item Number of trees: $\{50, 100, 200, 500\}$
					\item Maximum tree depth: $\{\texttt{None}, 2, 3, 5, 10, 20, 30\}$
					\item Minimum samples per leaf: $\{1, 5, 10, 20\}$
					\item Minimum samples for split: $\{2, 10, 20\}$
					\item Feature selection strategy: $\{\texttt{None}, \texttt{sqrt}, \texttt{log2}\}$
				\end{itemize}

				\paragraph{Linear Regression}
				\noindent
				For Linear Regression, the focus was placed on feature selection rather than model regularization, as the underlying estimator is deterministic.
				A univariate statistical feature selection method based on the F-test was employed to study the impact of dimensionality reduction.
				Both raw and log-transformed target variants were considered.

				\begin{itemize}
					\item Feature selection method: \texttt{SelectKBest} with F-statistic
					\item Number of selected features: $\{2, 3, 5, 10, 20, 30, \texttt{all}\}$
				\end{itemize}

				\paragraph{K-Nearest Neighbors Regressor}
				\noindent
				For the KNN model, hyperparameters governing neighborhood size, distance metrics, and weighting strategies were explored.
				Given the sensitivity of KNN to scale and noise, both standard and transformed-target variants were evaluated.

				\begin{itemize}
					\item Number of neighbors: $\{1, 3, 5, 10, 20, 30, 50, 100\}$
					\item Weighting scheme: $\{\texttt{uniform}, \texttt{distance}\}$
					\item Search algorithm: \texttt{ball\_tree}, \texttt{kd\_tree}, \texttt{brute}, \texttt{auto}
					\item Distance metric: $p \in \{1, 2\}$ (Manhattan and Euclidean)
				\end{itemize}

				\paragraph{Gradient Boosting Regressor}
				\noindent
				Histogram-based Gradient Boosting was chosen due to its efficiency on tabular data.
				The hyperparameter grid focused on tree depth, learning rate, and the number of boosting iterations.
				As with previous models, both standard and log-transformed target variants were examined.

				\begin{itemize}
					\item Maximum tree depth: $\{3, 5, 7\}$
					\item Learning rate: $\{0.05, 0.1\}$
					\item Number of boosting iterations: $\{200, 400\}$
				\end{itemize}

				\paragraph{Support Vector Regression}
				\noindent
				For Support Vector Regression, both linear and radial basis function (RBF) kernels were evaluated.
				The regularization strength, $\epsilon$-insensitive loss width, and kernel parameters were systematically varied.
				Log-transformed target variants were included to mitigate sensitivity to extreme price values.

				\begin{itemize}
					\item Regularization parameter $C$: $\{0.1, 1, 10, 100\}$
					\item $\epsilon$-insensitive loss: $\{0.01, 0.1, 0.2, 0.5\}$
					\item Kernel type: \texttt{linear}, \texttt{rbf}
					\item RBF kernel coefficient $\gamma$: $\{\texttt{scale}, 0.01, 0.1, 1\}$
				\end{itemize}

				\medskip
				\noindent
				After completing the hyperparameter search, the best-performing configuration from each model class was selected based on cross-validation performance and subsequently compared on a held-out test set.
				\noindent For every model mentioned in the section~\ref{subsubsec:Model Selection} we did hyperparameter (fine) tuning.
				After which we took all the best performing models from each model class and compared them to one another.

	\subsection{Model Selection}
		\noindent When it came to model selection we usually had two big criteria:
		\begin{enumerate}
			\item The model should generalize well, hence it should perform good on testing data
			\item The model should have a smaller error on the test data relative to the baseline error (since the baseline error was taken from the test data)
		\end{enumerate}

		\noindent This means that we should first look at tables~\ref{tab:model_performance_sales_R2} and~\ref{tab:model_performance_rents_R2} and pick the ones that had the highest $R^2$ score
		as this meant that the model was able to explain most of the variance that appeared in the data that it has never seen before. \newline

		\noindent If we have had a hard time picking between the models based just on $R^2$ score, we would then go to tables~\ref{tab:model_performance_sales_NMAE} and~\ref{tab:model_performance_rents_NMAE}
		and pick out models that had the lowest Mean Absolute Error, because these models made the smallest mistakes and if this wasn't enough we also had tables~\ref{tab:model_performance_sales_NRMSE}
		and~\ref{tab:model_performance_rents_NRMSE} to help us make decisions based on the Root Mean Square Error. \newline

		\noindent And on top of that we had plots of comparing each models Predicted Value to the True Value (Ground Truth). \newline

		\noindent For \textbf{sales} we decided to go with the \emph{Support Vector Machine}, and for \textbf{rents} we decided to go with \emph{K-Nearest Neighbors}
